# Video Dancer audit — 10 September 2026

Video Dancer has a coherent core: storyboard plans, immutable takes, and timeline instances. The highest-value next work is to make saving, project switching, recovery, and export dependable before expanding the feature set.

Audited application version: **0.17.1**, application commit **57b1600**. Scope: `C:/Claude/vi-dancer`, the consumed source in `C:/Claude/koan-shared/vidancer-ui` and selected shared infrastructure, plus the public documentation in `C:/Claude/video-dancer`. The public documentation directory is not the application source.

## Evidence and limits

- `npm run typecheck`: passed.
- `npm run build`: passed, including main process, preload, and renderer.
- Three isolated probes against bundled application source reproduced the persistence/import/recovery-file defects below. [Results](audit-2026-09-10/results.json) and [reproduction script](audit-2026-09-10/reproduce.cjs) are retained. The script deliberately asserts the existing broken behavior; it is an audit reproducer, not a regression suite certifying correct behavior.
- Source review covered project persistence, render submission/recovery, export, release configuration, onboarding, modal behavior, and the shared renderer structure. This is a targeted audit, not a line-by-line review of every provider and panel.
- No live provider submissions, user-project edits, installed-app interaction, GPU rendering, macOS testing, or packaged-installer testing were performed. Performance observations are structural, not measured UI latency. The build and all synthetic project writes stayed in the workspace.
- No application source was changed. Audit files and synthetic fixtures were added; the normal build regenerated ignored output/assets.

## Ranked findings

### 1. P1 — A failed project save still counts as a successful take landing

**Reproduced.** Simulating a failed write made `addTake()` resolve successfully. The new clip existed in memory, but the project on disk still had zero clips. A save-failure notification was correctly emitted, so the failure is visible; the operation's success contract is the problem.

`saveProject()` catches the write error and returns a resolved promise. `addTake()` awaits that promise and reports success. The render handler then removes the paid render's recovery entry. If the user exits before another successful save, the take registration and automatic recovery route can both be lost; the downloaded media file may still exist.

Evidence: [saveProject](C:/Claude/vi-dancer/src/main/project.ts:332), [addTake](C:/Claude/vi-dancer/src/main/project.ts:830), [recovery-entry retirement](C:/Claude/vi-dancer/src/main/index.ts:2617).

**Fix:** propagate persistence failure to the caller while keeping the internal save queue usable. Retire a pending render only after durable project persistence succeeds. Keep a retryable unsaved state.

**Acceptance:** force a failed write/rename during a paid take landing; the operation must not report durable success and the pending request must survive. Retry the save, reopen the project, and verify exactly one take.

### 2. P1 — Asynchronous imports and recovery can write into the wrong project

**Import race reproduced.** Start importing an image in project A, pause its file copy, open project B, and finish the copy. The file is written under A, but its library entry is inserted into B.

`importImage()` reads the global current project both before and after an `await`. Video import has the same ownership pattern across probing/transcoding. Recovery checks the active project before fetching a result, but does not recheck it after the download before calling global project mutations. The live video render path has a post-render guard, but its subsequent reference-image imports still introduce another switch window.

Evidence: [image import](C:/Claude/vi-dancer/src/main/project.ts:775), [video import](C:/Claude/vi-dancer/src/main/project.ts:2122), [recovery](C:/Claude/vi-dancer/src/main/index.ts:230), [live render landing](C:/Claude/vi-dancer/src/main/index.ts:2556).

**Fix:** give each asynchronous job an explicit project/session owner and commit through that owner. Validate ownership after awaited work and before state mutation. A path check alone is insufficient if A is closed and reopened while work is running. Preserve deferred results for their original project.

**Acceptance:** switch A→B and A→B→A during image copy, video transcode, and recovered-result download. No foreign paths or deltas may enter the active project, and the result must remain recoverable in A.

### 3. P1 — The desktop runtime is out of support

**Verified locally and against the upstream release notice.** The application installs Electron **31.7.7** and specifies `^31.0.0`. Electron's own [31.7.7 release page](https://releases.electronjs.org/release/v31.7.7) states that the 31.x series has reached end of support. This is an update-maintenance risk, not a claim that this audit demonstrated an exploit.

Evidence: [runtime dependency](C:/Claude/vi-dancer/package.json:62). Existing protection is useful: CSP, sandboxed windows, navigation restrictions, and masked settings responses are already present.

**Fix:** upgrade to a supported Electron line in a dedicated compatibility change. The renderer explicitly relies on legacy `File.path`; migrate that integration as part of the upgrade rather than only changing the version number.

**Acceptance:** packaged Windows/macOS smoke checks for launch, file drops, media seeking, OAuth login, preload APIs, local GPU processes, and updating.

### 4. P2 — Exported dissolves do not match the preview

**Confirmed in source; already acknowledged in public documentation.** The export builds a fade-to-black on the outgoing segment. The monitor's transition is a true crossfade. A cut approved in the editor therefore changes visually in the delivered MP4. This also conflicts with the source README's broad claim that what is scrubbed is what exports.

Evidence: [segment construction](C:/Claude/vi-dancer/src/main/export.ts:432), [export fade filter](C:/Claude/vi-dancer/src/main/export.ts:502), [README promise](C:/Claude/vi-dancer/README.md:197).

**Fix:** implement overlap compositing for export using the same transition timing as preview. Until that ships, expose the limitation beside the export action and make the documentation consistent.

**Acceptance:** compare preview and exported frames across a red→blue dissolve, then repeat with trims, speed changes, an in/out range, and an FX bake. Check audio through the transition too.

### 5. P2 — An unreadable recovery ledger is treated as empty and can be overwritten

**Reproduced.** A malformed `pending-renders.json` returned an empty list. Adding another request replaced it with a ledger containing only the new request.

`readAll()` handles a missing file, malformed JSON, and other read failures identically. Atomic writes reduce corruption risk but do not make every unreadable file equivalent to a new project.

Evidence: [ledger read](C:/Claude/vi-dancer/src/main/pending.ts:90), [subsequent rewrite](C:/Claude/vi-dancer/src/main/pending.ts:111).

**Fix:** return empty only for a genuinely absent file. Preserve/quarantine malformed data, report the recovery problem, and refuse a destructive replacement until recovery is resolved. Observe and surface errors from pending-entry writes as well.

**Acceptance:** malformed JSON and access-denied reads preserve the original file and produce a recoverable error; a missing file initializes normally.

### 6. P2 — Recovery stops checking jobs that are still running after reopening

**Confirmed control flow; no provider call performed.** Opening a project schedules one recovery pass. An upstream job still running during that pass is retained but not checked again until another project open. A user can leave the application open after restarting and never see the completed paid render arrive.

Evidence: [running-result branch](C:/Claude/vi-dancer/src/main/index.ts:268), [one-shot scheduling](C:/Claude/vi-dancer/src/main/index.ts:373); all call sites are project-open handlers.

**Fix:** represent recovered jobs in the Queue and poll them with bounded backoff while their project is open. Stop polling on project switch, resume it on return, and prevent overlapping recovery passes before their first asynchronous read.

**Acceptance:** reopen while a mocked provider job is running, then let it complete. It must appear without another reopen and without duplicate takes.

### 7. P2 — A release tag does not identify all the code that ships

**Confirmed configuration defect.** The release workflow clones the current default branch of `koan-shared`, which now includes the renderer and shared models/types. It does not select an immutable commit. Rebuilding an old application tag can produce a different UI; Windows and macOS jobs can also consume different revisions if that branch moves between clones. App-level lockfiles do not pin the content of these local file dependencies.

Evidence: [shared checkout](C:/Claude/vi-dancer/.github/workflows/release.yml:38), [local package dependencies](C:/Claude/vi-dancer/package.json:50).

**Fix:** record an immutable shared-package revision with each application release and build both operating systems against it. Include application and shared revisions in diagnostics/build metadata.

**Acceptance:** rerun the same tag after advancing the shared default branch; both jobs still consume the recorded revision.

### 8. P2 — Modal dialogs lack keyboard isolation and basic dialog semantics

**Confirmed in source; live keyboard interaction remains to be tested.** The shared modal has no dialog role, accessible title binding, focus trap, initial focus, or focus restoration. Its close control is a clickable span. Meanwhile timeline shortcuts run on the window in capture phase and guard editable text fields, but not a modal being open; that handler also omits `SELECT` from its typing guard.

This leaves keyboard focus and editing commands insufficiently isolated from the timeline behind a dialog.

Evidence: [modal shell](C:/Claude/koan-shared/vidancer-ui/src/ui/Modal.tsx:25), [timeline shortcut guard](C:/Claude/koan-shared/vidancer-ui/src/panels/Timeline.tsx:2661).

**Fix:** use semantic buttons, a labelled modal dialog, focus containment/restoration, and one shared rule that suppresses background editing shortcuts while a modal is active.

**Acceptance:** keyboard-only Settings navigation; Tab stays within the dialog, Escape closes only the active dialog, and Delete/Ctrl+K cannot modify the timeline behind it.

### 9. P2 — Onboarding no longer explains the available ways to start

**Confirmed in source.** The first-launch modal teaches API-key suppliers, includes a parked Higgsfield API option, and omits the current Bridge login and local-rendering routes. This is inconsistent with the current product offering described by the README. It also labels stored credentials as connected, including after a validation failure, and fal's “save & test” action does not pass a validation function.

Evidence: [welcome flow](C:/Claude/koan-shared/vidancer-ui/src/panels/WelcomeModal.tsx:78), [validation status](C:/Claude/koan-shared/vidancer-ui/src/panels/WelcomeModal.tsx:51), [fal action](C:/Claude/koan-shared/vidancer-ui/src/panels/WelcomeModal.tsx:102).

**Fix:** offer three clear starting routes: storyboard now, connect a cloud supplier/login, or set up local rendering. Distinguish “saved,” “verified,” and “failed.” Generate supplier choices from the same capability data used by the model selector.

**Acceptance:** a fresh user can reach a playable storyboard without credentials; each cloud/local route leads to its actual setup; invalid keys never show “connected.”

## Improvement sequence

| Order | Work | Completion evidence |
|---|---|---|
| 1 — Protect work and paid results | Save-failure contract, explicit project ownership, preserved recovery ledgers, continuing recovery | Turn the three reproducers into passing regression tests; add delayed-provider and restart tests |
| 2 — Make shipping repeatable | Pin the shared revision, add checks on pull requests, update Electron | Same source revisions on both platforms; packaged compatibility checks pass |
| 3 — Make the editing result trustworthy | Export/preview transition parity and modal shortcut isolation | Deterministic media fixtures and keyboard interaction checks |
| 4 — Improve first use | Current onboarding routes, accurate connection status, synchronized teaching surfaces | A clean-profile first-storyboard/first-render walkthrough |

There is no normal test script in the application manifest, and the supplied workflow gates releases on type checking and building rather than behavior. The immediate useful tests are persistence failure, project ownership, render recovery, and short deterministic export fixtures. Type correctness alone did not catch the reproduced bugs.

## Product and maintenance opportunities

Preserve the storyboard-first model, visible beat structure, immutable take recipes, and per-instance take selection. These are the project's strongest organizing ideas. Atomic serialized saves, undo history, protected checkpoint media, partial export files, panel error boundaries, and thumbnail caching also provide useful foundations to extend.

- **Make project state and render state legible:** persistent saved/unsaved feedback, explicit original-project ownership in the Queue, and visible recovery status would make failures easier to understand and resolve.
- **Separate source footage from supplier proxies:** video import currently normalizes non-friendly footage to a 720-short-side H.264 copy. That is useful for provider references, but preserving a project-owned original would support higher-quality editing/export and future provider-specific proxies. Treat this as a product enhancement, not an undisclosed import defect.
- **Extract shared timeline decisions gradually:** preview and export still duplicate timing/take-resolution rules. Centralize pure decisions and test them before splitting larger components. `Timeline.tsx` is 3,823 lines, `project.ts` 3,727, and main IPC setup 3,084; these are change-risk indicators, not proof of poor runtime performance.
- **Measure before optimizing:** the built renderer entry is about 2.14 MB uncompressed. Measure startup, panel-open latency, scrolling, and scrubbing on a representative large project before deciding whether to split panels or change state subscriptions.
- **Consolidate documentation:** public README/manual, developer README, historical addenda, onboarding, and What's New can disagree. Pick a maintained feature/capability source and verify teaching surfaces when behavior changes.

Suggested next implementation scope: finish the first row of the improvement sequence, including regression coverage, before adding another generation engine.
